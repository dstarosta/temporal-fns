Getting Started

temporal-fns Guide

temporal-fns is a date utility library with the same functions you already know from date-fns — but built on Temporal instead of Date.

JavaScript's built-in Date has some well-known rough edges: it's mutable, timezones are awkward, and months are zero-indexed. Temporal is the new built-in API that fixes all of that. The only catch is that it has a different API, so switching means rewriting how you work with dates.

temporal-fns solves that by giving you the same function names you'd use in date-fns — addDays, compareAsc, differenceInCalendarDays, eachDayOfInterval, and so on — except they take and return Temporal values. You get the familiar API and the better date engine underneath.

Why use it:

  • Feels like date-fns — same function names, same arguments. If you've used date-fns before, you already know most of this API.
  • No Date footguns — values are immutable, timezones are explicit, and months are numbered the way you'd expect (January is 1, not 0).
  • Import only what you use — every function is also its own package entry point, so your bundle only includes the functions you actually call.
  • Handles the hard parts for you — daylight saving time, leap years, and months of different lengths are handled correctly because Temporal handles them correctly.
  • Typed — written in TypeScript, so your editor knows what each function expects and returns.
Getting Started

Installation

Requirements

You'll need TypeScript 5.9+ and a runtime that supports Temporal — that's the latest Chrome/Edge/Firefox, or Node.js 26+.

bash
npm install temporal-fns

Then import whatever functions you need, just like you would with date-fns:

typescript
import { addDays, compareAsc } from 'temporal-fns';

If you want your bundler to include only the functions you actually use, import each one from its own subpath instead:

typescript
import { addDays } from 'temporal-fns/add-days';
import { compareAsc } from 'temporal-fns/compare-asc';
No native Temporal?

We recommend targeting an environment with native Temporal support rather than relying on a polyfill — polyfills can't fully replicate the spec and aren't guaranteed to behave correctly in every case. If you have no other option, @js-temporal/polyfill is the most complete one available, but treat it as a stopgap, not a long-term solution.

Getting Started

Philosophy

Date has been a known source of bugs for as long as JavaScript has had it. Months are zero-indexed, for one. Timezone handling is the deeper problem — a Date is just a UTC timestamp plus whatever offset the current system zone happens to report for it. It can carry an offset like +02:00, but an offset isn't a zone: several IANA zones share the same offset at any given moment, and the same zone's own offset changes across a DST transition. A Date has no memory of which zone it was actually meant to represent — only of the instant itself.

Date is also mutable, and the methods that change it (setDate, setHours, and the rest) mutate in place rather than returning a new instance. Pass a Date into a function, and that function can change the caller's copy without anyone intending it to — there's no way to hand out a Date and be sure it'll still hold the same value later. This is the kind of bug that's easy to introduce and hard to track down, since the mutation can happen far from where the value is read.

Temporal is the language's answer to all of this — immutable values, sane calendar fields, and explicit zone-aware types (PlainDate, PlainDateTime, ZonedDateTime) that make timezone handling something you opt into rather than something you can silently get wrong. temporal-fns exists to make moving from Date to Temporal a small change instead of a rewrite, while also fixing the rough edges that date-fns and its companion packages have accumulated over time.

1. Drop-in compatible with date-fns

If you're coming from date-fns, almost everything carries over directly — same function names, same arguments, same behavior, just operating on Temporal values instead of Date. This includes date-fns-tz, not just date-fns core — between the two, temporal-fns implements every function except constructFrom (a low-level internal helper) and transpose, putting compatibility at ~99%. See Differences from date-fns for the full list and the reasoning behind each one.

2. One library instead of several

With date-fns, timezone support and some interval helpers end up living in separate packages and mental models. temporal-fns folds all of that into one library:

  • Works with every Temporal type — PlainDate, PlainDateTime, PlainTime, PlainYearMonth, and ZonedDateTime. Date is also fully supported everywhere and is noticeably faster, since it skips the Temporal conversion overhead — but the Temporal types give you immutability and unambiguous timezone handling that Date can't. Use whichever fits your case; the function you call stays the same either way.
  • Timezones are built in, the way date-fns-tz bolts them on for date-fns.
  • A handful of extra interval methods inspired by Luxon's Interval class (set operations like intersecting or subtracting intervals) are included natively.
  • Several long-standing date-fns bugs are fixed rather than carried over.

See Bugs, Performance, and Size for the details and the bugs we found and fixed along the way.

3. No dependencies

temporal-fns has zero runtime dependencies. It relies on the native Temporal object and nothing else — no transitive packages, no surprise version bumps, no supply-chain surface beyond temporal-fns itself.

Getting Started

Differences from date-fns

Every commonly used function in date-fns and date-fns-tz has a temporal-fns equivalent with the same name and the same signature — you import it from temporal-fns instead of date-fns, and pass it a Temporal value (or a plain Date, which is also fully supported) instead of a Date. There are exactly two exceptions, and both are skipped on purpose rather than left out by oversight.

constructFrom and transpose

constructFrom(date, value) and transpose(date, constructor) exist in date-fns as a generic construction mechanism: they let date-fns' own functions build a result using whatever Date subclass the input came from, rather than hard-coding Date. This is how extensions like @date-fns/utc's UTCDate or @date-fns/tz's TZDate work — they subclass Date, and constructFrom calls new date.constructor(value) to produce another instance of that same subclass.

That mechanism doesn't carry over to Temporal, and not just as a matter of taste — it's a real construction mismatch:

  • Temporal.PlainDate, PlainDateTime, and ZonedDateTime are not subclasses of Date, so there's no shared constructor contract for constructFrom to dispatch through in the first place.
  • constructFrom's whole contract assumes a constructor that takes one value — a timestamp. Temporal.PlainDate's constructor takes year, month, and day as three separate required arguments. Calling it the way constructFrom calls Date — new Temporal.PlainDate(value) — throws a RangeError immediately, because month and day are missing. There's no way to make the two contracts line up; one constructor takes a single timestamp, the other requires three calendar fields.
  • transpose builds on the same pattern and then mutates the result with setFullYear/setHours. Temporal values are immutable, so even setting aside the construction mismatch above, there's no equivalent in-place step to port.

In short: porting these two as-is wouldn't just be extra work, it would reintroduce the exact class of silent-wrong-value bug that switching to Temporal is meant to eliminate. See Bugs for other cases where date-fns' Date-based design produces incorrect results that Temporal avoids by construction, and Performance for how the Date fast paths temporal-fns uses instead compare in speed.

A few functions render slightly different text

date-fns ships hand-written English text for a handful of functions — words like "about", "last", and "at" baked directly into the output. temporal-fns generates that text through Intl instead, so it comes out correct in any locale — but for a few functions, that means the English text itself reads a little differently too. Some common examples:

typescript
formatRelative(sixDaysAgo, now);
// date-fns:      "last Thursday at 1:40 PM"
// temporal-fns:  "last week"

formatDistance(oneYearAgo, now);
// date-fns:      "about 1 year"
// temporal-fns:  "1 year"

format(date, 'P');
// date-fns:      "06/19/2026"
// temporal-fns:  "6/19/26"  (matches Temporal.PlainDate's own toLocaleString)
// Want "06/19/2026" instead? format(date, 'MM/dd/yyyy') gives that directly.

Bugs

While porting date-fns function by function, we ran every function's test suite against the real, installed date-fns package as a parity check. Six cases turned up where temporal-fns and date-fns deliberately disagree — not because of a translation mistake, but because we found a genuine bug in date-fns itself and chose to fix it rather than carry it over. Each one is demonstrated by a test that diffs real date-fns output against temporal-fns, not just an assertion of the "correct" value in isolation.

1. formatISODuration silently drops weeks

date-fns' Duration type declares weeks?: number, and formatISODuration accepts a Duration — but its output template never references weeks at all. Every other field renders; weeks is the one silent exception.

typescript
import { formatISODuration as dateFnsFormatISODuration } from 'date-fns';
import { formatISODuration } from 'temporal-fns';

dateFnsFormatISODuration({ years: 1, weeks: 2, days: 3 });
//=> 'P1Y0M3DT0H0M0S'   (the 2 weeks vanished)

formatISODuration({ years: 1, weeks: 2, days: 3 });
//=> 'P1Y0M2W3DT0H0M0S'  (weeks included)

2. Unit converters silently round to -0

Nine of date-fns' unit-conversion helpers (monthsToYears, millisecondsToHours, secondsToMinutes, and six others) use Math.trunc() to convert between units. For small negative inputs, Math.trunc() produces -0 instead of 0 — and only one of the nine (daysToWeeks) happens to guard against it.

typescript
import { monthsToYears as dateFnsMonthsToYears } from 'date-fns';
import { monthsToYears } from 'temporal-fns';

Object.is(dateFnsMonthsToYears(-1), -0); //=> true   (looks like 0, but isn't)
Object.is(monthsToYears(-1), -0); //=> false  (returns 0)

3. Narrow "noon" token parses to midnight

date-fns' parse matches day-period text (am/pm/noon/midnight) against a lookup table. For the narrow width (BBBBB/bbbbb/aaaaa), the documented and self-produced narrow form for noon is the single letter 'n' — but the parser's own regex for matching it is /^no/i, which doesn't match a lone 'n'. The lookup silently fails and falls through to the default case: midnight.

typescript
import { parse as dateFnsParse } from 'date-fns';
import { parse } from 'temporal-fns';

const reference = new Date(2020, 0, 1);
dateFnsParse('n', 'BBBBB', reference).getHours(); //=> 0   (midnight, wrong)
parse('n', 'BBBBB', reference).getHours(); //=> 12  (noon, correct)

4. differenceInBusinessDays isn't antisymmetric across time zones

A correct difference function should satisfy f(a, b) === -f(b, a) always. date-fns' differenceInBusinessDays (with @date-fns/tz's TZDate) doesn't, when the two dates carry different IANA zones. Its day-by-day counting loop is seeded from whichever argument is "earlier," and that argument's own embedded time zone drives the whole walk — so swapping which date is "earlier" silently swaps which zone's calendar the count uses.

typescript
import { differenceInBusinessDays as dateFnsDifferenceInBusinessDays } from 'date-fns';
import { differenceInBusinessDays } from 'temporal-fns';
import { TZDate } from '@date-fns/tz';

const ny = new TZDate(2026, 4, 15, 20, 0, 0, 'America/New_York');
const sg = new TZDate(2026, 4, 12, 0, 0, 0, 'Asia/Singapore');

dateFnsDifferenceInBusinessDays(ny, sg); //=> 4
dateFnsDifferenceInBusinessDays(sg, ny); //=> -3
// 4 + -3 !== 0, not antisymmetric

const nyZone = 'America/New_York';
const sgZone = 'Asia/Singapore';
const nyZoned = Temporal.ZonedDateTime.from(`2026-05-15T20:00:00-04:00[${nyZone}]`);
const sgZoned = Temporal.ZonedDateTime.from(`2026-05-12T00:00:00+08:00[${sgZone}]`);

differenceInBusinessDays(nyZoned, sgZoned); //=> 3
differenceInBusinessDays(sgZoned, nyZoned); //=> -3   (correctly antisymmetric)

// date-fns: magnitude 4 one way, 3 the other way - inconsistent
// temporal-fns: magnitude 3 both ways - consistent

How Temporal helped: this is the one bug where Temporal itself is the fix, not just an opportunity to notice the bug while porting. temporal-fns converts both arguments to their own Temporal.PlainDate — each read in its own zone — before the day-counting walk starts. Once both inputs are reduced to a zone-independent type, there's no embedded zone left for the walk to pick up; the order you pass the two arguments in can no longer change which calendar the counting happens against. The bug exists in date-fns precisely because Date/TZDate carry zone information on the instance that downstream code can accidentally key off of — Temporal.PlainDate has no zone to carry, so the whole bug class is structurally impossible.

5. intervalToDuration silently drops weeks too

The same Duration.weeks gap from bug #1 shows up a second time, in a different function. intervalToDuration's day-by-day decomposition goes years → months → days → hours → minutes → seconds — it never reports weeks, no matter how many full weeks the remainder spans.

typescript
import { intervalToDuration as dateFnsIntervalToDuration } from 'date-fns';
import { intervalToDuration } from 'temporal-fns';

const start = new Date(2014, 8, 1, 10, 19, 50);
const end = new Date(2017, 5, 15, 15, 29, 20);

dateFnsIntervalToDuration({ start, end });
//=> { years: 2, months: 9, days: 14, hours: 5, minutes: 9, seconds: 30 }

intervalToDuration({ start, end });
//=> { years: 2, months: 9, weeks: 2, hours: 5, minutes: 9, seconds: 30 }

6. setYear overflows into the next month on Feb 29

date-fns' setYear goes through native Date#setFullYear, which rolls over into the next month when the target year doesn't have the requested day — setting the year on Feb 29 to a non-leap year lands on March 1, not a clamped Feb 28. Notably, date-fns' own setMonth doesn't have this problem; it clamps correctly. Only setYear was inconsistent with it.

typescript
import { setYear as dateFnsSetYear } from 'date-fns';
import { setYear } from 'temporal-fns';

dateFnsSetYear(new Date(2024, 1, 29), 2030); //=> Mar 1 2030  (overflowed)
setYear(new Date(2024, 1, 29), 2030); //=> Feb 28 2030 (clamped)

How Temporal helped: this is where Temporal made the fix nearly free. Temporal's .with() defaults to overflow: 'constrain' — clamping out-of-range fields instead of rolling them over — so setting just the year is a single date.with({ year }) call, with no month-by-month walk required. date-fns' own implementation, by contrast, calls a native Date method whose overflow-by-rollover behavior it has no way to opt out of.

See Differences from date-fns for the two cases where we judged a date-fns construction pattern as fundamentally incompatible with Temporal rather than fixable.

Getting Started

Performance

For Date input — the case most migrating users hit first — temporal-fns is faster than date-fns, not just comparably fast. For Temporal-typed input, the picture depends heavily on the function and the JS engine, since native Temporal support is still new and engines are at different points in optimizing it.

Snapshot, not a permanent ceiling

The numbers below are a point-in-time benchmark measured 2026-06-23, against Node 26.3.1 (V8), Chromium 149 (V8), and Firefox 151 (SpiderMonkey), and date-fns 4.4.0 / date-fns-tz 3.2.0. Temporal is a genuinely new engine feature — expect these numbers, especially the Temporal-typed columns, to shift as engines invest more in Temporal-specific optimizations. Re-benchmark against your own target environment if performance is a hard requirement.

Date input: faster than date-fns on every tested engine

Five common operations (format, parse, addDays, compareAsc, eachDayOfInterval over a 365-day range) were benchmarked with Date input against the real, installed date-fns package, using tinybench (Node) and an identical methodology under Playwright for Chrome and Firefox — same fixtures, same iteration counts, same median-of-7-samples timer.

typescript
// Total time for format + parse + addDays + compareAsc + eachDayOfInterval,
// summed across all 5 calls, Date input only:
//
//                 date-fns  temporal-fns  % of date-fns
// Node (V8)     169,868 ns    97,251 ns          57.3%
// Chrome (V8)   150,600 ns    78,404 ns          52.1%
// Firefox       111,320 ns    94,458 ns          84.9%

temporal-fns' Date-input total comes out to roughly half to five-sixths of date-fns' time, depending on the engine — a real, measured win on every engine tested, not a single-engine fluke. The two functions doing the most work (addDays and eachDayOfInterval's internal comparisons) have a fast path that operates on Date directly instead of round-tripping through Temporal for every call.

Temporal-typed input: correctness has a cost, and it's engine-dependent

Passing a Temporal.PlainDate, PlainDateTime, or ZonedDateTime instead of a Date is slower for arithmetic-heavy operations, because those go through real Temporal.*.prototype.add()/.with() calls — that's the inherent cost of calendar-correct, immutable arithmetic, not a temporal-fns inefficiency on top of it. How much slower varies a lot by engine:

  • In V8 (Node and Chrome), Temporal-typed totals for the same 5-function benchmark run about 10–20x the Date total.
  • In Firefox/SpiderMonkey, the same comparison is only about 1.7–3.3x the Date total — SpiderMonkey's Temporal implementation is currently more optimized relative to its own engine baseline.
  • ZonedDateTime is consistently the most expensive of the three Temporal types in every engine, since it resolves a real IANA timezone/offset on top of the date math. PlainDate is consistently the cheapest, since it has the fewest fields to handle.

The size of that gap is the more interesting number than either side of it on its own. V8 and SpiderMonkey are running the exact same Temporal operations, on the same benchmark, and landing 5–10x apart from each other — that's not Temporal itself being slow, it's a difference in how much JIT optimization work each engine has put into its Temporal implementation so far. SpiderMonkey's result is a working proof that Temporal-typed arithmetic doesn't have to cost 10–20x a Date equivalent; V8 closing that gap looks like an engineering and prioritization question for V8, not a ceiling Temporal itself imposes. Date got the same multi-decade optimization investment (inline caching, shape specialization) that Temporal is only starting to receive now — expect this gap to narrow as engines catch up, the same way it already has in Firefox.

The four timezone functions ported from date-fns-tz (getTimezoneOffset, toZonedTime, fromZonedTime, formatInTimeZone) don't follow this pattern — temporal-fns wins on all four, on every engine, by 2–13x, for any input type:

typescript
// date-fns-tz -> temporal-fns, Date input (Node):
//
// getTimezoneOffset  9,033 ns ->  1,418 ns  (6.4x)
// toZonedTime        5,197 ns ->  1,917 ns  (2.7x)
// fromZonedTime      9,694 ns ->  1,785 ns  (5.4x)
// formatInTimeZone  92,998 ns -> 44,008 ns  (2.1x)

These four are faster across the board because date-fns-tz hand-rolls its own offset-parsing and DST-hole-fixup logic, where temporal-fns just asks Temporal.ZonedDateTime to resolve the offset — DST transitions and gaps are handled natively, with no manual fixup loop required. Unlike the arithmetic functions above, Temporal-typed input costs about the same as Date input here, since all four immediately convert to an instant/epoch-milliseconds internally regardless of what type came in.

See Bugs for the correctness fixes found along the way, and Size for how the same design choices affect bundle weight.

Getting Started

Size

For the common case — importing a handful of functions, not the whole library — temporal-fns is exactly as tree-shakable as date-fns, and just as small. Importing everything is a closer comparison, because temporal-fns folds in capability that date-fns spreads across two packages.

Snapshot, not a permanent ceiling

Measured 2026-06-23 via real esbuild --bundle --minify output (not raw file sizes), against date-fns 4.4.0 and date-fns-tz 3.2.0. Re-measure against your own bundler and dependency versions if exact byte counts matter for your build.

Per-function import: same as date-fns

Most consumers import a handful of functions, not the entire library. Bundled and minified via esbuild, temporal-fns produces byte-identical output whether you import from the package root or a direct subpath — confirming tree-shaking works end to end — and stays just as small as the date-fns equivalent:

typescript
// Minified / gzipped, esbuild --bundle --minify:
//
// addDays alone                     763 B /   ~415 B
// addDays + isWithinInterval      1,447 B /   ~613 B
// format alone (heaviest single) 11,371 B / ~3,780 B

The sub-1KB result holds for arithmetic/comparison/predicate-class functions like addDays or isWithinInterval, whether imported from the package root (from 'temporal-fns') or a direct subpath (from 'temporal-fns/add-days') — both produce identical bytes. It doesn't extend to Intl-backed functions like format/parse, which carry real weight regardless of how few functions you import alongside them — date-fns has the same characteristic for the same reason.

Whole-library import: slightly larger, because it does more

Importing the entire public API is a less realistic case, but it's where the size comparison gets interesting, because date-fns alone doesn't cover everything temporal-fns covers out of the box. To match date-fns-tz's timezone functions and a useful subset of Luxon's interval-algebra operations using only date-fns, you'd need three things, not one: date-fns core, the separate date-fns-tz package, and your own hand-written set-algebra helpers on top of Interval's plain { start, end } object, since neither date-fns package provides them.

typescript
// Whole-API import, minified / gzipped (esbuild --bundle --minify):
//
// date-fns alone                                     70.9 KB / 17.8 KB
// date-fns-tz alone (date-fns marked external)        8.8 KB /  3.3 KB
// date-fns + date-fns-tz combined (deduped once)     79.7 KB / 21.0 KB
// temporal-fns (timezones + interval algebra incl.)  84.7 KB / 23.6 KB

Importing everything, temporal-fns comes out about 1.06x the minified size and 1.13x the gzipped size of date-fns + date-fns-tz combined. The extra ~5 KB comes from two sources, not one. Part of it is new functions with no date-fns equivalent at all: 11 interval set-algebra functions (intersectIntervals, unionIntervals, subtractInterval, areIntervalsAdjacent, areIntervalsEquivalent, isIntervalSubset, isIntervalSuperset, isIntervalEmpty, splitIntervalByDuration, sliceInterval, countIntervalUnits) plus two timezone-identity functions (getTimezoneId, timeZoneIds) for real IANA zone identity rather than just offset math. The rest is the Temporal overloads and type-dispatch logic added to functions that do have a date-fns equivalent — every ported function accepts Date and all three Temporal types, which means extra overload signatures and an instanceof branch per function that date-fns, with only Date to support, never needed.

The 11 set-algebra functions cover the same ground, in set-theory terms, as Luxon's Interval class is known for: intersection, union (envelope), difference/complement, equivalence, adjacency, subset, and superset, plus partitioning an interval into fixed-size chunks. date-fns' own Interval shape — a plain { start, end } object, which temporal-fns deliberately keeps instead of wrapping in a class — has none of these; date-fns only ships areIntervalsOverlapping and isWithinInterval on top of it. Reaching the same operation coverage starting from date-fns means writing and maintaining that set-algebra layer yourself; temporal-fns ships it, as part of the extra ~5 KB alongside the per-function Temporal logic described above.

See Bugs and Performance for the other two angles on the same set of design choices.

Examples

Format date

Same functions, same arguments, same output as date-fns — just import from temporal-fns instead.

typescript
import { format, formatDistance, formatRelative, subDays } from 'temporal-fns';

format(new Date(), "'Today is a' eeee");
//=> "Today is a Wednesday"

formatDistance(subDays(new Date(), 3), new Date(), { addSuffix: true });
//=> "3 days ago"

formatRelative(subDays(new Date(), 3), new Date());
//=> "last week"
Examples

I18n

date-fns ships a separate locale per language, imported by name (date-fns/locale's es, ru, and so on). temporal-fns has no locale files at all — pass any BCP 47 locale string straight through to the native Intl object the runtime already ships with.

typescript
import { intlFormat, intlFormatDistance, subDays } from 'temporal-fns';

const dateOptions = { year: 'numeric', month: 'long', day: 'numeric' };

intlFormat(new Date(2026, 5, 19), dateOptions, { locale: 'es' });
//=> "19 de junio de 2026"

intlFormat(new Date(2026, 5, 19), dateOptions, { locale: 'ja' });
//=> "2026年6月19日"

intlFormatDistance(subDays(new Date(), 3), new Date(), { locale: 'es' });
//=> "hace 3 días"

intlFormatDistance(subDays(new Date(), 3), new Date(), { locale: 'ru' });
//=> "3 дня назад"
Zero-weight

None of this pulls in bundled locale data — date-fns' locale/ directory is over 5 MB raw across every language combined. Intl already ships with the JS runtime at no bundle cost, for every locale it supports.

Examples

Composition & FP

temporal-fns mirrors date-fns/fp: every function has a curried, data-last counterpart under temporal-fns/fp, generated directly from the same implementation as the regular export.

typescript
import { addYears, formatWithOptions } from 'temporal-fns/fp';

const addFiveYears = addYears(5);

const dateToString = formatWithOptions({ locale: 'es' }, 'd MMMM yyyy');

const dates = [
  new Date(2017, 0, 1),
  new Date(2017, 1, 11),
  new Date(2017, 6, 2),
];

const toUpper = (arg: unknown) => String(arg).toUpperCase();

const formattedDates = dates.map(addFiveYears).map(dateToString).map(toUpper);
//=> ['1 ENERO 2022', '11 FEBRERO 2022', '2 JULIO 2022']
Examples

Arithmetic & Comparison

The everyday building blocks — add/subtract a unit, compare two dates, measure the gap between them — work exactly like their date-fns counterparts.

typescript
import { addDays, isAfter, differenceInDays } from 'temporal-fns';

addDays(new Date(2026, 5, 19), 10);
//=> Mon Jun 29 2026

isAfter(new Date(2026, 5, 20), new Date(2026, 5, 19));
//=> true

differenceInDays(new Date(2026, 5, 30), new Date(2026, 5, 19));
//=> 11
Examples

Intervals

date-fns' interval helpers carry over directly, and temporal-fns adds the set-algebra operations covered in Size — intersection, union, difference, and the rest — natively, with no separate library to reach for.

typescript
import { eachDayOfInterval, intersectIntervals } from 'temporal-fns';

const june1to3 = { start: new Date(2026, 5, 1), end: new Date(2026, 5, 3) };
eachDayOfInterval(june1to3);
//=> [Mon Jun 01 2026, Tue Jun 02 2026, Wed Jun 03 2026]

const firstHalf = { start: new Date(2026, 5, 1), end: new Date(2026, 5, 10) };
const secondHalf = { start: new Date(2026, 5, 5), end: new Date(2026, 5, 15) };
intersectIntervals(firstHalf, secondHalf);
//=> { start: Fri Jun 05 2026, end: Wed Jun 10 2026 }
Examples

Temporal Types

Every function also accepts Temporal.PlainDate, PlainDateTime, and ZonedDateTime directly — the same function, no separate Temporal-specific API to learn, with the result coming back as the same concrete type you passed in.

typescript
import { addDays, format } from 'temporal-fns';

// ZonedDateTime in, ZonedDateTime out — DST-correct by construction
const meetingZone = 'America/New_York';
const meeting = Temporal.ZonedDateTime.from(`2026-03-07T12:00:00-05:00[${meetingZone}]`);
addDays(meeting, 1);
//=> 2026-03-08T12:00:00-04:00[America/New_York]  (offset correctly flips across DST)

// PlainDate in, formatted directly — no Date round-trip
format(Temporal.PlainDate.from('2026-06-19'), 'PPP');
//=> "June 19th, 2026"
Examples

Time Zones

The four functions ported from date-fns-tz work the same way, built on Temporal.ZonedDateTime instead of hand-rolled offset parsing — see Bugs and Performance for what that buys you.

typescript
import { fromZonedTime, toZonedTime, formatInTimeZone } from 'temporal-fns';

// 10 AM local time in Los Angeles, expressed as a UTC Date:
const localTime = new Date(2026, 5, 19, 10, 0, 0);
const utc = fromZonedTime(localTime, 'America/Los_Angeles');
//=> 2026-06-19T17:00:00.000Z
